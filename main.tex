\begin{abstract}
Tool-using AI agents are increasingly reached over the network through the
Model Context Protocol (MCP), which turns a personal automation stack into an
Internet-facing HTTP service. We study what a single operator can realistically
put in front of such an endpoint. We evaluate a full-stack defense deployed in
front of a self-hosted 29-tool MCP gateway published through a Cloudflare
tunnel. The evaluation uses a reproducible harness of 32 scenarios across nine
experiments---including adaptive adversaries, protocol fuzzing, timing
side-channel analysis, multi-run latency with confidence intervals,
post-authentication content defense, active deception, and a
false-positive/evasion corpus---run across four revisions: the unmodified
admission gate (v1), a hardened revision (v2), a credential-scoping extension
(v3), and a post-authentication content defense layer (v4). v1 had no false
blocks on benign MCP sessions and stopped declared crawlers, single-source
credential probing and floods at \SI{5}{\micro\second} median overhead (v1) and
\SI{9}{\micro\second} (v2). It also
had measurable weaknesses, all caused by keying state on individual client IPs:
distributed guessing went unbanned (700 guesses, 0 bans), ban-list lookups grew
linearly (\SI{21.7}{\milli\second} per request at 50k bans), rate-limit memory
was unbounded (\SI{87}{MB} at 100k sources), and there were further gaps in IPv6
rotation, header trust and lockout. v2 closes each of these with a small local
change. Latency stays flat at \SI{0.13}{\milli\second} up to 50k bans
($169\times$ faster), memory is capped (\SI{18.8}{MB} at 100k sources),
distributed guessing earns 95 bans, IPv6 rotation inside a /64 costs one ban
instead of 200, and a mistyped token costs 5 minutes rather than an hour. v3
extends defense past the admission layer: scoped tokens and per-tool rate
limiting bound the blast radius of a leaked credential. v4 adds
\bastion{}, a post-authentication content defense module: input validation
blocks SQL injection, command injection and path traversal in tool arguments
with zero false positives on three natural-language test phrases; behavioral
analysis detects catalog enumeration and tool-cycling reconnaissance; output
filtering redacts nine classes of secrets (AWS keys, private keys, JWTs,
bearer tokens, HTTP Basic credentials, passwords, API keys, GitHub tokens,
Slack tokens) from tool
results before they leave the server, with an optional honeytoken mode that
replaces redacted secrets with trackable canary credentials for attacker
attribution; and a batch-size cap closes the JSON-RPC batch bypass
identified in v3.
A million-request standard stress suite (10 traffic categories) and a
million-request hard-mode suite (WAF bypass, protocol abuse, behavioral
mimicry, timing evasion, resource exhaustion) confirm zero false blocks on
benign sessions, \textgreater99\% block rates on admission-layer threats, and
expose a measured bypass: all 100{,}000 WAF-evasion payloads (comment
obfuscation, Unicode homoglyphs, double encoding) passed \bastion{}'s
pattern-based detection, and false-positive rates on natural-language inputs
reached 90\% on adversarially crafted benign phrases. Median latency stays
below \SI{5}{ms} across \num{2000000} requests on an i3-3220 server.
\ifrealdata
Over a \RTHours-hour public exposure (\RTRequests{} requests from \RTSources{}
sources), replaying the same real trace through each policy shows v1 blocking
\RTvOneBlocked{} requests at the gate and v2 blocking \RTvTwoBlocked{}.
\fi
We release the harness, stress tooling, trace-replay tooling and aggregate results.
\end{abstract}

\section{Introduction}
Agent frameworks let a language model call tools~\citep{yao2023react,schick2023toolformer,patil2023gorilla},
and MCP standardizes how those tools are exposed over stdio or HTTP~\citep{mcpspec}.
An MCP server published on a public hostname inherits every property of an
Internet service. Internet-wide scanners find it~\citep{durumeric2013zmap}. AI
data collectors crawl it, and their volume and opt-out behaviour are in
flux~\citep{longpre2024consent,rfc9309}. Others probe it for credentials. Unlike
a static website, the thing behind the door can \emph{act}. The security
community has responded: surveys catalogue tool poisoning and over-privileged
servers~\citep{hou2025mcp,owaspllm2025}; benchmarks quantify tool-poisoning
success rates above 72\%~\citep{mcptox2025}; and the NSA has published formal
design guidance~\citep{nsamcp2026}. Yet a recent systematic review of 73
defense studies~\citep{tamayo2026slr} finds that all existing work targets
post-authentication threats; none measures what happens at the admission
layer. We study the full request lifecycle---from the first byte to the
final response---asking what a single operator can realistically put in
front of such an endpoint with no external dependencies.
Enterprises answer with identity-aware proxies and managed bot defense.
Individual developers who self-host an MCP server often have only the server
process itself.

\begin{enumerate}
  \item[\textbf{RQ1}] Does a small, dependency-free admission gate stop the
        unwanted traffic an exposed agent endpoint attracts, without blocking
        legitimate MCP clients?
  \item[\textbf{RQ2}] Where, measurably, does per-client-IP defense break down?
  \item[\textbf{RQ3}] Can those failures be fixed locally, and at what cost?
  \item[\textbf{RQ4}] How do the policies compare on real Internet traffic?
  \item[\textbf{RQ5}] Does the gate hold against adaptive adversaries and
        protocol-level abuse?
  \item[\textbf{RQ6}] Can tool-call content be defended post-authentication
        without false-blocking legitimate agent interactions?
  \item[\textbf{RQ7}] Can output filtering be extended to active deception
        that attributes credential exfiltration without altering the
        benign-client experience?
\end{enumerate}

\noindent\textbf{Contributions.}
(i) A deployed defense for an MCP endpoint that combines an admission gate,
bearer authentication and capability minimization (\cref{sec:design}).
(ii) A reproducible evaluation of the unmodified code, with eight quantified
weaknesses (\cref{sec:v1}).
(iii) A hardened revision and a before/after comparison on identical scenarios
(\cref{sec:v2}).
(iv) A post-authentication extension with scoped tokens and per-tool rate
limiting, evaluated on two new scenarios (\cref{sec:v3}).
(v) A post-authentication content defense module (\bastion{}) that validates
tool arguments, detects behavioral anomalies and redacts secrets from tool
results, evaluated on eight new scenarios (\cref{sec:bastion}).
(vi) An active-deception extension that replaces redacted secrets with
trackable honeytokens for attacker attribution, evaluated on two additional
scenarios (\cref{sec:honeytoken}).
(vii) A \num{2000000}-request stress evaluation across 20 traffic and
adversarial categories, confirming zero false blocks on benign sessions and
quantifying the evasion boundary of pattern-based content defense
(\cref{sec:stress}).
(viii) A time-boxed public exposure whose trace is replayed through every
policy (\cref{sec:real}).
(ix) A post-authentication risk-adaptive routing extension (\mirage{}) that
replaces the binary content decision with graded in-band lanes---including a
format-matched synthetic shadow lane and verifiable per-result provenance---and
is evaluated on a deployed loopback service (\cref{sec:mirage}).
(x) Release of the harness, stress tooling, replay tooling and aggregate data.

\noindent\textbf{Claim.} \emph{For a single-operator, Internet-exposed MCP
endpoint, a lightweight application-layer gate combined with a
high-entropy bearer token and a minimized tool surface stops declared
crawlers, credential probing, path scanning and floods at microsecond
cost with no false blocks on benign MCP sessions. It is effective only
if its state is keyed on network sources rather than individual addresses
and bounded in size. Scoped tokens and per-tool rate limits bound the
blast radius of a leaked credential. A post-authentication content
defense layer---input validation, behavioral analysis and output
filtering---extends protection to tool-call content without false
positives on natural-language tool inputs. An optional honeytoken mode
replaces redacted secrets with trackable canary credentials, providing
attribution when exfiltrated tokens are used. The token, not the gate,
remains the security boundary.}

\section{System and Threat Model}\label{sec:design}

\subsection{Deployment}
The protected service is \kit{}, a personal tool gateway that exposes one
29-tool catalog (DevOps monitoring, a shell assistant, a personal-memory
agent, a breach monitor and a homelab reconnaissance agent) over stdio and
MCP Streamable HTTP~\citep{mcpspec}. It is part of a broader personal
automation stack that includes local model inference (Ollama on a 24\,GB
Apple-silicon machine), a self-hosted Linux server (Docker, Grafana, Supabase)
and a Tailscale mesh. A single operator cannot justify an enterprise gateway for
this kind of stack, which motivates a lightweight, dependency-free gate.

The HTTP server binds to loopback, and a
\code{cloudflared} tunnel~\citep{cftunnel} is the only path from the Internet
(\cref{fig:arch}). The socket peer is therefore always loopback, so the client
identity is taken from the \code{CF-Connecting-IP} header set at Cloudflare's
edge~\citep{cfheaders}.

\subsection{Threat model}
\textbf{What this work addresses.}
Remote, unauthenticated adversaries send arbitrary HTTP requests through
Cloudflare:
(T1) \emph{declared} crawlers and scanners that name themselves in the
\code{User-Agent};
(T2) \emph{undeclared} crawlers that spoof a browser user-agent;
(T3) credential probers using one or many sources;
(T4) flooders;
(T5) path scanners;
(T6) adversaries who rotate addresses, for example within an IPv6 /64.
The goals are to prevent unauthorized tool execution, bound the operator's
resource cost and provide visibility.

An operator who does not need external access can avoid all of these by not
exposing the endpoint at all---for example, binding only to a Tailscale
address or removing the Cloudflare tunnel. This work targets endpoints that
are \emph{intentionally} Internet-facing, where unauthenticated traffic is an
operational reality.

\smallskip\noindent\textbf{What this work does not address.}
A leaked or stolen bearer token gives the holder full access to the
exposed tool surface. \sys{} does not detect or prevent this: once a
request carries a valid token, it is treated as authorized.
v3 scoped tokens (\cref{sec:v3}) reduce the \emph{blast radius}---a leaked
monitoring token cannot call shell or logging tools---but they do not
prevent use of the leaked credential within its scope. v4 \bastion{}
(\cref{sec:bastion}) adds post-authentication content defense---input
validation, behavioral analysis and output filtering---but these are
pattern-based checks, not semantic understanding of intent.

Threats that exploit the model's \emph{reasoning} are out of scope.
Tool poisoning (a malicious tool description that misleads the
model)~\citep{mcptox2025}, indirect prompt injection (a document or webpage
that tricks the model into making unintended tool
calls)~\citep{greshake2023indirect}, and trust escalation across
sessions~\citep{trustshift2026} are all attacks by or through
\emph{authorized} clients. Defending against them requires client-side
guardrails or sandboxed execution~\citep{cascade2026,nsamcp2026}.

Also out of scope: a compromised operator machine, Cloudflare itself, and
volumetric DDoS absorbed at the edge.

\subsection{Guardian v1}
\sys{} v1 (\code{guardian.py}, 263 lines, Python standard library only) makes
one decision per request, before authentication or JSON-RPC parsing:
\begin{enumerate}
\item an unexpired ban returns \code{403};
\item a case-insensitive match against 38 crawler and scanner signatures
      (\code{gptbot}, \code{claudebot}, \code{ccbot}, \code{bytespider},
      \code{sqlmap}, \code{nuclei}, \ldots) bans the client and returns
      \code{403};
\item more than 120 requests in 60\,s returns \code{429}~\citep{rfc6585}
      without a ban.
\end{enumerate}
A bearer token~\citep{rfc6750} is then checked in constant time. Eight
\code{401}s within 300\,s trigger a 60-minute ban, in the style of
\texttt{fail2ban}~\citep{fail2ban} and in line with online-guessing
guidance~\citep{nist80063b}. Bans and a JSONL access log are file-backed so
that a separate stdio process can offer operator tools; rate counters live in
memory. A \textbf{capability filter} removes all 15 \code{local\_only} tools
(offensive recon, breach lookups, the \sys{} controls themselves) and an
operator denylist from \code{tools/list} and \code{tools/call}.

\section{Evaluation Method}\label{sec:method}
The harness (\code{artifact/harness2.py}) launches an unmodified server tree
as a separate process on a private port, with a fresh 320-bit bearer token and
a fresh state directory for every scenario. It emulates the Cloudflare hop by
setting \code{CF-Connecting-IP} to documentation-range
addresses~\citep{rfc5737,rfc3849} and replays the scenarios over HTTP/1.1. The
base scenario set (S1--S14) runs against the v1, v2, v3 and v4 trees under the
shipped default policy. Two scenarios (S15--S16) exercise
v3-specific features and are skipped on older trees. Six advanced scenarios
(S17--S22) test adaptive adversaries, protocol-level abuse and implementation
robustness (\cref{sec:robust}). Eight scenarios (S23--S30) exercise
v4 \bastion{}'s post-authentication content defense (\cref{sec:bastion}).
Two scenarios (S31--S32) evaluate honeytoken injection (\cref{sec:honeytoken}).
E9 runs a false-positive corpus of 50 realistic natural-language tool inputs
and an evasion suite of 30 adversarial payloads (SQL comment obfuscation,
case mixing, encoding tricks, Unicode homoglyphs) against \bastion{}'s
injection detection.
Latency is measured end to end on a keep-alive connection: 50 warm-up requests,
then $3\times\num{1000}$ interleaved requests per condition (E2), or 500 per
point for ban-list scaling. E6 repeats the measurement 5 times ($\num{2500}$
samples per condition) and reports 95\% confidence intervals
(\cref{sec:latstat}). Memory is measured with \code{tracemalloc} in a fresh
interpreter. Platform: Apple M5 Pro, macOS 26.6.1, Python 3.12.13. Every number
is read from \code{artifact/results\_v\{1,2,3,4\}.json}. E8 scenarios
(S31--S32) are unit tests that toggle \code{BASTION\_HONEYTOKEN} to
\code{inject} and verify the output against the original.

\section{Guardian v1: Effective, but Keyed on the Wrong Thing}\label{sec:v1}

\finding{What works (RQ1).} On benign traffic, four MCP client user-agents
completed the protocol handshake and 100/100 calls with no false blocks (S1).
A client performing OAuth discovery and an SSE probe before connecting (S1b)
was also unaffected. All 38 declared crawler and scanner signatures were
blocked on the first request, and they stayed blocked after switching to a
benign UA \emph{with the valid token} (S2). A single-source prober was banned
on exactly its 8th failure (S4). A 300-request burst was held to exactly 120
served, with no collateral effect on other clients and recovery after the
window (S6). Over HTTP, \code{tools/list} returned 5 of 29 tools. Each of the
15 \code{local\_only} tools was unlisted and returned JSON-RPC \code{-32601}
when called directly (\code{artifact/surface.json}). The ablation with \sys{}
disabled (S11) served the entire flood and answered every guess.

\finding{What breaks (RQ2).}
\textbf{W1}~Spoofed browser UAs evaded the signature rule 38/38 times (S3);
the token still rejected all of them.
\textbf{W2}~Spreading 700 guesses over 100 sources produced 0 bans and 700
answered guesses (S5).
\textbf{W3}~Each request re-parsed the whole ban file. Median latency rose
from \SI{0.12}{\milli\second} with no bans to \SI{0.54}{}, \SI{3.99}{} and
\SI{21.7}{\milli\second} at \num{1000}, \num{10000} and \num{50000} bans
(\cref{fig:bans}).
\textbf{W4}~Per-IP rate state was never evicted: \SI{87.4}{MB} for
\num{100000} sources ($\sim$\SI{870}{B} each).
\textbf{W5}~Rotating through 200 addresses in one IPv6 /64 created 200 ban
entries (S12), which feeds W3. An end site typically holds at least a
/64~\citep{rfc6177}, so this is cheap for an attacker.
\textbf{W6}~Path scanning (S7) returned only \code{404}/\code{405} and was never
penalized.
\textbf{W7}~Eight mistyped tokens locked a legitimate user out for 60\,min
(S8).
\textbf{W8}~Several smaller gaps (S9--S11). \code{DELETE} bypassed the gate
and was not logged. Banned clients could still make the server read 256\,KB
bodies. On a non-loopback bind, such as the supported tailnet mode, forged
\code{CF-Connecting-IP} headers evaded a ban 5 out of 5 times. With \sys{}
disabled, unenforced ban records were still written.

\finding{Results (RQ3).} \Cref{tab:ba} gives the full comparison. Every
targeted weakness changed as intended, and the benign scenarios (S1, S1b) were
unchanged: no false blocks, and OAuth-discovery 404s are not treated as
scanning. The costs are small and measurable. v2's gate overhead is
\SI{9}{\micro\second} (median, gate on vs.\ off), up from v1's
\SI{5}{\micro\second}, both operationally negligible. Memory per tracked key rises slightly (${\approx}\SI{940}{B}$
against \SI{870}{B}), but the total is now bounded.

\finding{Trade-offs.} Keying on /64 means that separate customers who share a
/64, which some hosting providers do, share a fate. The global alarm lets a
distributed attacker tighten the threshold for everyone for up to 300\,s. The
worst case is a legitimate user needing 3 attempts instead of 8, which the
allowlist removes. The LRU cap means an attacker with more than \num{20000}
active sources can push out counters. Bans are persisted separately and are
not evicted.

\section{Post-Authentication Extension: Guardian v3}\label{sec:v3}
v1 and v2 treat the bearer token as monolithic: one token grants access to
every public tool. Once the token leaks---from a client's configuration, an
agent's context window, or a log line---the holder has the full tool surface.
And once authenticated, a client faces only the global rate limit, so a
misbehaving or compromised agent can call one tool hundreds of times without
triggering throttling.

\subsection{Scoped tokens}
v3 replaces the single token with a set of named tokens, each scoped to a list
of tool names (or \code{["*"]} for full access). The legacy single token remains
accepted as a full-access credential for backward compatibility.
\code{tools/list} returns only the tools the presenting token can reach, and
\code{tools/call} to an out-of-scope tool returns JSON-RPC \code{-32601}
without executing.

\subsection{Per-tool rate limiting}
v3 adds a per-(source, tool) sliding window on top of the global rate limit.
The default is 30 calls per 60\,s per tool per source. Exceeding it returns
JSON-RPC \code{-32005}; other tools and other sources are unaffected.
Allowlisted sources are exempt, consistent with the admission gate.

\finding{Results.}
S15 verifies token scoping: a full-access token sees all 5 public tools; a
scoped token sees only its 2 allowed tools (\code{devops\_status},
\code{devops\_health}); calling \code{devops\_logs} with the scoped token
returns \code{-32601}. S16 verifies per-tool rate limiting: with a limit of
10 calls per 60\,s, the first 10 calls to \code{shell\_explain} are served
and the next 20 return \code{-32005}; a different tool
(\code{shell\_suggest}) from the same source is unaffected.

\finding{Cost.} Both features add no measurable per-request latency:
they are checked inside \code{\_handle\_filtered} after authentication
succeeds, using the same sliding-window and LRU data structures as the
admission gate. Token lookup is a linear scan of the token set (typically
2--5 entries) with constant-time comparison per token. Total added code:
32 lines across three files.

\section{Post-Authentication Content Defense: Bastion v4}\label{sec:bastion}
v1--v3 control \emph{who} reaches the tools and \emph{how often}. They do not
inspect \emph{what} an authenticated client sends or what comes back. A
compromised or malicious agent with a valid token can send injection payloads
in tool arguments, enumerate the tool catalog for reconnaissance, or extract
secrets from tool responses. v4 adds \bastion{} (\code{bastion.py}, 394
lines, standard library only), a post-authentication content defense module
with three layers and an active-deception mode.

\subsection{Layer~4: Input validation}
Before a \code{tools/call} reaches \code{mcp\_core.handle()}, \bastion{}
checks the argument dict:
\begin{enumerate}
\item \textbf{Size limits.} Total serialized arguments are capped at
      \num{32768}\,B; individual string fields at \num{8192}\,B.
\item \textbf{Schema validation.} Arguments are checked against the tool's
      JSON Schema from the registry: required fields, type conformance and
      rejection of unknown fields (when \code{additionalProperties} is false).
\item \textbf{Injection detection.} All string values are scanned against
      compiled regex patterns for SQL injection (10 patterns, e.g.\
      \code{UNION\textbackslash{}s+SELECT}, \code{DROP\textbackslash{}s+TABLE}),
      command injection (8 patterns, e.g.\ backticks, \code{\$()}, semicolons
      before known dangerous commands) and path traversal (5 patterns, e.g.\
      \code{../}, \code{/etc/passwd}, URL-encoded variants).
\end{enumerate}
Patterns require structural syntax, not bare keywords: ``why is the database
dropping connections?'' does not match because it lacks the \code{TABLE}
keyword after \code{DROP}. Patterns also handle SQL comment obfuscation
(\code{DROP/**/TABLE}) and whitespace variants. Tools whose purpose is to
receive shell syntax
(\code{shell\_explain}, \code{shell\_suggest}, \code{shell\_recall}) are
exempt from injection checks but still subject to size and schema validation.
Blocked calls return JSON-RPC error \code{-32003}. The mode is configurable
(\code{BASTION\_INPUT\_MODE}: \code{block} or \code{log}).

\subsection{Layer~5: Behavioral analysis}
\bastion{} tracks per-source call patterns using the same sliding-window and
LRU data structures as \sys{}:
\begin{itemize}
\item \textbf{Enumeration.} More than 10 \code{tools/list} calls from one
      source in 120\,s triggers a behavioral block (\code{-32004}).
\item \textbf{Tool cycling.} More than 15 distinct tools called by one
      source in 120\,s (a reconnaissance pattern) triggers the same.
\end{itemize}
Legitimate MCP clients call \code{tools/list} once per session; the threshold
is generous. Behavioral blocks are returned on \code{tools/list} and
\code{tools/call} alike, so an enumerating client is stopped at the next call.

\subsection{Layer~6: Output filtering}
After a tool executes, \bastion{} scans the result text for nine secret
patterns (compiled at module load):
AWS access keys (\code{AKIA\ldots}), private keys
(\code{-----BEGIN\ldots PRIVATE KEY-----}), bearer tokens, HTTP Basic
credentials, password fields in config, API-key fields, JWTs
(\code{eyJ\ldots}), GitHub personal access tokens (\code{ghp\_\ldots}) and
Slack tokens (\code{xox[bpras]-\ldots}). Matches are replaced in-place with
\code{[REDACTED:\textit{type}]}, preserving the surrounding text. Responses
exceeding \num{524288}\,B are truncated with a \code{[TRUNCATED]} marker.

\subsection{Batch-size cap}
v4 also enforces a configurable cap on JSON-RPC batch size (default 20
messages per HTTP POST). This closes the batch bypass identified in S19
(\cref{sec:robust}): a batch of 100 \code{tools/list} calls now returns
HTTP 400 instead of being processed as one request.

\subsection{Active deception: honeytoken injection}\label{sec:honeytoken}
When \code{BASTION\_HONEYTOKEN} is set to \code{inject}, Layer~6 replaces
detected secrets with realistic-looking canary credentials instead of
\code{[REDACTED:\textit{type}]} markers. Each secret type receives a
format-appropriate honeytoken: AWS keys get a fake \code{AKIA}-prefixed
access key; JWTs get a structurally valid token whose payload contains a
canary marker and a unique tracking identifier; bearer tokens, GitHub PATs,
Slack tokens and Basic~Auth credentials are replaced with format-conforming
fakes; password and API-key fields preserve the surrounding
\code{key\,=\,"value"} structure and substitute only the secret value.

Every injection is logged to a JSONL audit file with a unique token
identifier, secret type, source IP and tool name. The HTTP server exposes
a \code{/canary/\textit{id}} callback endpoint---outside the \sys{} gate
so that it is reachable from arbitrary infrastructure---that logs a
callback hit (source IP and user-agent) when an attacker attempts to use
an exfiltrated honeytoken. The callback returns \code{404} to avoid
revealing the canary mechanism.

The mode defaults to \code{off}; when disabled, Layer~6 behaves identically
to passive redaction. Benign clients never see honeytokens in normal
operation because tool responses should not contain secrets---the
honeytoken fires only when a real secret would otherwise have been leaked.

\section{Robustness Under Adaptive and Protocol-Level Attacks}\label{sec:robust}
The scenarios in \cref{sec:v1,sec:v2} use na\"ive adversaries: each follows a
fixed script. A publishable evaluation must also test whether the gate holds
against adversaries that adapt, abuse protocol features, or target the
implementation rather than the policy. We add six scenarios (S17--S22).

\finding{Timing side-channel (S17).}
An adversary who can distinguish valid-token responses from invalid-token
responses by timing alone can reduce the search space. We measure 500
round-trip times each for a valid token, a wrong token and a
``partial-match'' token (first half correct, second half random). All three
conditions use constant-time comparison (\code{secrets.compare\_digest}).
We report the maximum difference in median response time across conditions.
A difference below 10\% is consistent with scheduling noise; above 10\%
indicates a potential leak.

\finding{Slow-and-low probing (S18).}
An adversary that stays just under the global rate limit (1.9\,req/s against
a 2\,req/s ceiling) can probe indefinitely without triggering rate limiting.
We send 228 wrong-token requests over ${\sim}120$\,s and record whether the
auth-failure mechanism bans the source.

\finding{Batch request abuse (S19).}
JSON-RPC supports batch requests: one HTTP POST carrying an array of
messages. The global rate limit counts HTTP requests, not JSON-RPC messages,
so a batch of 100 \code{tools/list} calls counts as one request.
We test batches of 100 and 1{,}000 messages and a 300\,KB oversize payload.

\finding{Protocol fuzzing (S20).}
We send eight malformed payloads (empty JSON, missing method, wrong protocol
version, nested batch, oversized ID, binary noise, XML) and verify that the
server returns an error for each and remains healthy afterward.

\finding{Session fixation (S21).}
The MCP spec assigns a session ID via the \code{Mcp-Session-Id} header after
\code{initialize}. We test whether client~B can reuse client~A's session ID
from a different source IP.

\finding{Post-ban recovery (S22).}
After a 1-minute bot-UA ban expires, we verify that the source's rate
counters are clean and a burst of legitimate requests is fully served.

Results for S17--S22 are in \cref{tab:advanced}; numbers are drawn from
\code{results\_v3.json}. \Cref{sec:latstat} reports latency with confidence
intervals.

S17 confirms that \code{secrets.compare\_digest} prevents timing leaks at
the application layer: 6.8\% median difference across conditions is well

auth-failure ban operates independently of the rate limit, catching slow
probers (banned at attempt 8 despite never exceeding 2\,req/s). S19 reveals
a concrete weakness: batch requests let an authenticated client multiply its
effective rate by the batch size (1{,}000$\times$) without triggering the
per-request limit. v4 closes this with a configurable batch-size cap
(\cref{sec:bastion}): batches exceeding 20 messages (default) are rejected
with HTTP 400 before processing. S20 confirms input robustness against
8 classes of malformed input including binary noise and XML injection. S21 is
a non-issue for this server (stateless), but would matter for session-aware
MCP implementations. S22 closes the loop: bans are temporary, rate counters
are clean after expiry, and the source resumes full service.

natural-language inputs range from 34\% (C10) to 90\% (H9) depending on
the adversarial crafting of the benign input. This quantifies the
fundamental limitation of pattern-based content defense on a protocol whose
tool arguments carry free-form text. A semantic-aware content filter
(e.g.\ an LLM-based classifier) could address both the evasion and
false-positive gaps, at a latency cost that would dominate the current
sub-\SI{5}{ms} gate.

\section{Statistical Rigor}\label{sec:latstat}
Single-run latency numbers (E2) are reproducible but do not quantify
measurement uncertainty. E6 repeats the latency measurement 5 times
($5 \times 500 = \num{2500}$ samples per condition) and reports 95\%
confidence intervals. The overhead of \sys{} on request latency is the
difference between the ``on'' and ``off'' distributions, matched by rank.

Over \num{2500} samples, median request latency is \SI{0.121}{\milli\second}
with \sys{} disabled and \SI{0.128}{\milli\second} with \sys{} enabled
(mean overhead \SI{5.2}{\micro\second}, 95\% CI
$[\SI{5.0}{\micro\second}, \SI{5.4}{\micro\second}]$).
The p95 latencies are \SI{0.154}{} and \SI{0.152}{\milli\second} respectively,
confirming that the tail is not widened. The overhead is operationally
negligible: \SI{5}{\micro\second} is ${\approx}0.001\%$ of a typical tool
execution time (seconds), and falls well within scheduling noise on any
non-real-time system. We report the CI to bound the measurement, not to
claim the difference matters.

\section{Related Work}

\finding{MCP threat landscape.}
Hou et al.~\citep{hou2025mcp} give the first survey of MCP security threats and
future directions. Javed et al.~\citep{mcpthreatmodel2026} apply STRIDE and
DREAD threat modeling across five MCP components and identify tool poisoning as
the most prevalent client-side vulnerability. The NSA's AI Security Center
published the first US government guidance on MCP
security~\citep{nsamcp2026}, warning that adoption has outpaced safeguards and
recommending controls including input screening, least-privilege interfaces,
audit logging, and overload protection. The Cloud Security Alliance provides
complementary practitioner guidance~\citep{csamcp2026}. OWASP catalogues
broader LLM application risks~\citep{owaspllm2025}, and Bajpai
et al.~\citep{mcpsafetyaudit2025} demonstrate major exploits against MCP-enabled
LLM systems.

\finding{Post-authentication attacks.}
The largest body of MCP security research studies what an authorized or
compromised client can do once inside. MCPTox~\citep{mcptox2025} benchmarks
tool poisoning across 45 live servers and 353 tools, finding attack success
rates above 72\%. MCP-ITP~\citep{mcpitp2026} automates implicit tool poisoning
generation in a black-box setting. TrustShiftProbe~\citep{trustshift2026}
characterizes staged trust-escalation attacks. Indirect prompt
injection~\citep{greshake2023indirect} targets authorized data paths. Our
threat model explicitly excludes all of these: we study the \emph{pre-authentication}
admission layer, not the post-authentication trust boundary.

\finding{Defense mechanisms.}
CASCADE~\citep{cascade2026} proposes a three-tiered local defense for
prompt-injection detection in MCP systems (regex and entropy pre-filtering,
semantic analysis, output filtering), evaluated on 5{,}000 samples at 95.85\%
precision. Tamayo~\citep{tamayo2026slr} surveys 73 studies and categorizes
existing MCP defenses into static analysis, runtime guardrails, middleware
access control and formal verification.
None of the 73 surveyed studies measures an admission-layer defense for an
Internet-exposed MCP endpoint.

\finding{Established network defense.}
Log-driven banning~\citep{fail2ban} and throttling of online
guessing~\citep{nist80063b} are long established. Timing side-channels in
string comparison are well understood~\citep{brumley2011remote}; constant-time
comparison (\code{secrets.compare\_digest} in Python, per the \code{hmac}
module) is the standard mitigation. Crawler consent rests on
convention~\citep{rfc9309}, and restrictions aimed at AI crawlers have grown
sharply~\citep{longpre2024consent}. Our S3 result confirms that
convention-based identification cannot be relied on.
Honeytokens---decoy credentials placed to detect unauthorized
access---were introduced by Spitzner~\citep{spitzner2003honeytokens} and are
available as a hosted service~\citep{canarytokens}. We apply the technique at
the MCP output-filtering layer, replacing leaked secrets in tool responses
with format-conforming canary credentials.

\finding{Comparison with alternatives.}
An operator can place several existing tools in front of an MCP endpoint:
Cloudflare WAF rules or Bot Management (paid, closed-source, no MCP awareness),
\code{nginx} rate limiting (per-IP, no auth-failure tracking, no ban persistence),
or \code{fail2ban} scanning the access log (log-driven, works after the fact,
no MCP-protocol awareness). Each addresses part of the threat surface, but none
provides MCP-specific tool filtering, JSON-RPC-aware rate limiting, or an
integrated evaluation against MCP client behaviour. \sys{} is not a replacement
for edge-layer defense; it is complementary. On this deployment, Cloudflare's
free tier provides DDoS absorption and TLS termination; \sys{} handles
everything between the tunnel exit and the MCP dispatch.

\finding{Relationship to OAuth.}
The MCP specification defines an authorization flow built on
OAuth~2.0~\citep{rfc6749,mcpauth2025}: a client discovers the server's
authorization endpoint, obtains a scoped access token through a standard grant,
and presents it as a bearer credential~\citep{rfc6750}. OAuth answers
\emph{``what is this authenticated client allowed to do?''}: it delegates
identity verification to an authorization server, issues tokens scoped to
specific capabilities, and assumes the client has been registered in advance.
\sys{} answers a different question---\emph{``should this unknown sender's
request reach the authentication layer at all?''}---using only behavioral
signals available before any credential is checked: source address, request
rate, user-agent signature, probe pattern and ban history. The two operate
at different layers of the request lifecycle (\cref{tab:oauthcmp}). OAuth
cannot stop a botnet from flooding the token endpoint or a scanner from
probing paths that do not exist; \sys{} cannot decide which tools a
legitimate user should access. An MCP endpoint can use both: \sys{} as the
pre-authentication admission gate, and OAuth for identity, delegation and
scope. In this deployment, the bearer token is a high-entropy static secret
rather than an OAuth-issued token, because the endpoint has a single
operator and no third-party clients; v3 scoped tokens
(\cref{sec:v3}) approximate OAuth's per-resource scoping without requiring
an authorization server. The evaluation results apply regardless of whether
the bearer credential is a static secret or an OAuth access token: the gate
runs before the credential is inspected, and \bastion{}'s content defense
runs after authentication succeeds, so the admission and content layers are
credential-scheme agnostic.

\finding{Gap.}
Prior work on MCP security either catalogues threats, studies post-authentication
attacks, or prescribes controls without empirical measurement. We contribute a
measured, before/after evaluation of admission-layer defense on a deployed,
Internet-facing MCP endpoint, show where per-address state fails, quantify
the cost of fixes on identical workloads, and test robustness against adaptive
and protocol-level attacks.

\section{Discussion}

\finding{Layered defense in practice.}
No single mechanism in this stack is individually novel. What the evaluation
demonstrates is that their \emph{combination}, applied specifically to an MCP
endpoint and measured against MCP client behaviour, produces a defense with
quantifiable properties: zero false blocks on benign sessions, measurable
overhead ($<$\SI{10}{\micro\second}), bounded resource consumption, and
visible degradation when attackers adapt. Each v1 weakness traced to a single
design choice (per-IP state keying) that produced measurable failures across
multiple scenarios. The v2 fix was correspondingly local.

\finding{The batch bypass, closed.}
S19 revealed that JSON-RPC batch requests let an authenticated client bypass
the per-request rate limit entirely. v4 \bastion{} closes this with a
batch-size cap (default 20 messages per POST): batches exceeding the cap
are rejected before dispatch. This trades strict JSON-RPC batch compliance
for safety. In our deployment logs, all observed MCP client implementations
(Claude Code, MCP Inspector, \code{python-httpx}) sent one message per
POST; the cap of 20 is conservative.

\finding{Input validation vs.\ natural language.}
The central tension in Layer~4 is that some tools accept free-form text
(e.g.\ \code{devops\_ask} takes natural-language questions about servers).
Naive keyword matching would false-block ``why is the database dropping
connections?'' as SQL injection. The solution has two parts: structural
patterns that require injection \emph{syntax} (e.g.\ \code{DROP TABLE}, not
just \code{drop}), and per-tool exemptions for tools whose purpose is to
receive shell syntax. S23 confirms zero false positives on three
natural-language phrases, and S24 confirms that exempt tools pass injection
payloads by design.

\finding{Active deception as a defense layer.}
Honeytokens shift output filtering from passive (redact and forget) to active
(replace and track). The key design constraint is that a legitimate client
should never see a honeytoken under normal operation: tool responses should
not contain secrets, so the honeytoken fires only on the same responses that
would have been redacted. The canary callback gives the operator something
passive redaction cannot: attribution of the attacker's infrastructure when
an exfiltrated credential is reused. The limitation is that credential-shaped
honeytokens only produce callbacks when the attacker actually tries the
credential against a service that reports the attempt (e.g.\ AWS CloudTrail
for canary AWS keys) or visits the callback URL~\citep{canarytokens}. An
attacker who collects but never uses the token is not detected.

\finding{Generalizability.}
This study covers one endpoint, one operator, one tool catalog. The
architecture is not specific to this deployment---it requires only HTTP
headers, a bearer token and a tool registry with JSON Schema---but the
scenario set, default thresholds and performance numbers are specific to the
platform. Other MCP deployments may face different traffic patterns, use
different transport modes (SSE, stdio proxy), or sit behind different CDNs
with different header semantics.

\section{Limitations}
This is a single-system, single-operator study. Controlled experiments ran on
loopback with an emulated Cloudflare hop, so edge behaviour is assumed rather
than measured, and the latency figures exclude network and tunnel time. The
benign workload covers concurrent multi-client sessions and rate-window
recovery (S13, S14) but not SSE streaming or mixed read/write tool workloads.
The v2 defaults (the /64 prefix, the 20k cap and the global-alarm thresholds),
v3 defaults (30 calls per tool per window) and v4 defaults (injection patterns,
batch cap, enumeration thresholds) are reasonable choices, not tuned optima.

\bastion{}'s input validation is pattern-based: it catches structural injection
syntax but cannot detect novel or obfuscated payloads. The \num{2000000}-request
stress evaluation quantifies both failure modes: 100\% of WAF-evasion payloads
(comment obfuscation, Unicode homoglyphs, double URL encoding, IFS tricks,
base64 evasion, polyglots) bypassed detection (H1, 0\% blocked), and
false-positive rates on natural-language inputs reached 90\% on adversarially
crafted benign phrases (H9). Output filtering catches nine
known secret formats but cannot detect proprietary or novel credential
patterns. Behavioral analysis uses fixed thresholds; adaptive adversaries
who stay just under the enumeration or cycling limit are not detected.
Honeytoken injection produces attribution only when the attacker reuses the
credential against a service that reports the attempt; silent collection is
not detected. Honeytokens for key-value patterns (passwords, API keys)
preserve the surrounding structure but change the value format, which could
alert a sophisticated attacker that the credential is fake.

The real-traffic window covers a single hostname whose discoverability depends
on certificate-transparency logs and DNS enumeration by third parties. The
techniques evaluated (rate limiting, UA signature blocking, auth-failure banning,
token scoping, injection detection, output redaction)
are individually well established; the contribution
is their measured application and failure modes in the MCP context, not the
techniques themselves.

\section{Conclusion}
A few hundred lines of dependency-free code in front of an MCP endpoint,
together with a strong token and a minimized tool surface, measurably stop
declared crawlers, credential probing, path scanning and floods at
microsecond cost. The first version failed where its state was keyed on
individual addresses and allowed to grow without bound. Distributed and
rotating adversaries slipped through, and a growing ban list turned the
defense into a latency liability. Keying on network sources and bounding
state fixed each measured failure without new false blocks. Extending
defense past authentication with scoped tokens and per-tool rate limits
bounds the blast radius of a leaked credential and prevents authorized
abuse of individual tools. \bastion{} closes the remaining post-auth
surface: injection patterns and schema validation catch malicious tool
arguments before execution, behavioral analysis detects reconnaissance and
enumeration, output filtering redacts secrets from tool responses, and an
optional honeytoken mode replaces redacted secrets with trackable canary
credentials that attribute credential exfiltration when the attacker reuses
them. Together, \sys{} and \bastion{} span the full request lifecycle from
first byte to final response in 32 targeted scenarios, six advanced
robustness scenarios, and \num{2000000} stress-test requests across 20
traffic categories. The stress evaluation confirms zero false blocks on
benign sessions across all volumes, and quantifies the evasion boundary:
standard WAF bypass techniques (comment obfuscation, Unicode homoglyphs,
double encoding) pass \bastion{}'s pattern-based detection entirely,
confirming that a semantic-aware content filter is needed for the
post-authentication layer. Self-hosted agent endpoints should treat such
gates as cost and visibility controls, and never as the authentication
boundary.
